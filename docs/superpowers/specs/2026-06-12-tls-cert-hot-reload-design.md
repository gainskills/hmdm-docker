# TLS certificate hot reload — Tomcat HTTPS connector + MQTT broker

**Date:** 2026-06-12 (updated 2026-06-13)
**Status:** Implemented in working tree; pending rebuild/runtime verification and commit
**Scope:** `templates/conf/server_template.xml`, `templates/conf/context_template.xml`, `docker-entrypoint.sh`

## Problem

Both TLS endpoints loaded their certificate **only at container startup**:
- the Tomcat HTTPS connector (8443) from a JKS keystore built by the entrypoint;
- the embedded MQTT broker (31000) from the same JKS.

When the certificate was renewed on disk, nothing picked it up without restarting
the whole `hmdm` container. Goal: pick up a renewed certificate **without a
restart**, using native Tomcat 11 capabilities (HTTPS) and the app's PEM-based
in-process reload (MQTT), driven by the operator's externally-managed cert files.

## Deployment assumptions (this environment)

- Certificates are **mounted as files**, not generated by the bundled certbot.
  The operator uses the "custom SSL certificates" path: `certbot` commented out,
  with `cert.pem` / `fullchain.pem` / `privkey.pem` under
  `./volumes/letsencrypt/live/$BASE_DOMAIN/` (mounted at
  `/etc/letsencrypt/live/$BASE_DOMAIN/`). Renewal is handled externally.
- The deployed WAR is the operator's **prefer-PEM build** (`gainskills/hmdm-server`)
  that reads `ssl.pem.key.path` / `ssl.pem.cert.path` (+ optional
  `ssl.pem.config.path`) and reloads the MQTT broker cert in-process. With both
  JKS and PEM available it prefers PEM.
- Tomcat 11 / JDK 21 (`tomcat:11-jdk21-temurin-noble`).

## Key findings

1. **Tomcat 11 native reload (HTTPS).**
   `org.apache.catalina.security.TLSCertificateReloadListener` (added 11.0.0-M12)
   monitors the loaded cert's expiry and reloads the TLS config a set number of
   days before expiry — no external watcher. Must be nested in `<Server>`.
   Defaults: `checkPeriod` 86400s (24h), `daysBefore` 14.

2. **PEM files work directly** in `SSLHostConfig` (`certificateKeyFile`,
   `certificateFile`, `certificateChainFile`) and interoperate with the listener,
   so the connector re-reads renewed files with no keystore rebuild.

3. **MQTT TLS via PEM (app-dependent).** The stock OS broker is plaintext
   (`addConnector("mqtt://" ...)`), but the deployed prefer-PEM build serves MQTT
   over TLS when the `mqtt.server.uri` scheme is `ssl://`, reading the cert from
   `ssl.pem.key.path` (privkey) + `ssl.pem.cert.path` (fullchain) and reloading
   in-process. The Paho client re-validates the server cert on each reconnect, so
   no client-side reload is needed. This wiring is therefore inert unless the
   deployed WAR implements `ssl.pem.*`.

## Design

### `templates/conf/server_template.xml`

1. Register the listener inside `<Server>` (built-in defaults, no attributes):
   ```xml
   <Listener className="org.apache.catalina.security.TLSCertificateReloadListener" />
   ```
2. Switch the 8443 connector's `<Certificate>` from JKS to PEM-direct:
   ```xml
   <Certificate certificateKeyFile="/etc/letsencrypt/live/_BASE_DOMAIN_/_HTTPS_PRIVKEY_"
                certificateFile="/etc/letsencrypt/live/_BASE_DOMAIN_/_HTTPS_CERT_"
                certificateChainFile="/etc/letsencrypt/live/_BASE_DOMAIN_/_HTTPS_FULLCHAIN_" />
   ```
   Drops `certificateKeystoreFile` / `certificateKeystorePassword` / `type="EC"`
   (Tomcat auto-detects RSA vs EC).

### `templates/conf/context_template.xml`

- `ssl.keystore.*` (JKS) **commented out** — legacy; PEM is preferred/active.
- `ssl.pem.key.path` / `ssl.pem.cert.path` **active**, pointing at the mounted PEMs
  (key = `privkey.pem`, cert = `fullchain.pem`); `ssl.pem.config.path` left
  commented (optional, defaults to a writable temp path).

### `docker-entrypoint.sh`

- **server.xml render `sed`:** substitute `_HTTPS_PRIVKEY_` / `_HTTPS_CERT_` /
  `_HTTPS_FULLCHAIN_`; `_SSL_KEYSTORE_PASSWORD_` removed from this render.
- **context.xml render `sed`:** add `_HTTPS_PRIVKEY_` / `_HTTPS_FULLCHAIN_`
  (so the active PEM params resolve).
- **MQTT scheme follows `PROTOCOL`:** when `PROTOCOL=https` and the embedded broker
  is used (`MQTT_EXTERNAL != 1`), rewrite `MQTT_SERVER_URI` scheme to `ssl://`,
  preserving host:port. External-broker URIs are left untouched.
  ```sh
  if [ "$MQTT_EXTERNAL" != "1" ] && [ "$PROTOCOL" = "https" ]; then
      MQTT_SERVER_URI="ssl://$(echo "$MQTT_SERVER_URI" | sed -E 's#^[a-z+]+://##')"
  fi
  ```
- **JKS build retired:** the `openssl`/`keytool` block is removed (nothing reads
  the JKS now). Replaced with a PEM existence check (keeps the certbot wait for
  `HTTPS_LETSENCRYPT=true`, then fails fast if any of privkey/cert/fullchain are
  missing).

### `docker-compose.yaml`

Unchanged. Renewal is external; `LOCAL_IP` is used when MQTTS is enabled.

## Behavior and limitations

- **HTTPS reload is expiry-driven**, not file-change-driven: checked every 24h,
  reloads when the loaded cert is within 14 days of expiry. Seamless for routine
  renewal. Emergency/early rotation isn't instant — `docker compose restart hmdm`
  forces immediate pickup.
- **MQTT TLS** activates only with an `ssl://` URI (now derived from
  `PROTOCOL=https`) and depends on the deployed prefer-PEM WAR; reload is handled
  in-process by that app.
- Existing TLS/MQTT connections are unaffected by a reload; only new handshakes
  use the new cert.

## Operational notes

- `conf/Catalina/localhost/ROOT.xml` (the rendered context) is **volume-persisted**
  (`./volumes/hmdm-config`) and only re-rendered when missing or
  `FORCE_RECONFIGURE=true`. Set `FORCE_RECONFIGURE=true` (or delete the volume's
  `ROOT.xml`) to pick up `context_template.xml` changes. `server.xml` re-renders
  every start.
- MQTTS over loopback needs the container to resolve `BASE_DOMAIN` to itself for
  TLS hostname validation — set `LOCAL_IP` (the entrypoint writes it to
  `/etc/hosts`).

## Out of scope

- Automating certificate renewal (handled externally by the operator).
- Switching to an external broker (EMQX / HiveMQ / Mosquitto) for MQTTS.
